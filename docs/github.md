# Одна рабочая папка и GitHub

Работаем только в `/home/kali/codex-AD/webscanner`. Это существующий Git-репозиторий с `origin` → `https://github.com/Aloha-sudo/Webscanner.git`. Отдельная папка для публикации больше не нужна.

## Что где находится

| Путь | Назначение | В GitHub |
| --- | --- | --- |
| `backend/`, `frontend/`, `cli/` | Рабочий код и тесты | Да |
| `docs/`, `examples/`, `scripts/` | Документация, синтетическое демо, инструменты | Да |
| `docker-compose.yml`, `.env.example` | Общая конфигурация запуска | Да |
| `.env`, `docker-compose.override.yml` | Параметры конкретного компьютера | Нет |
| `scans/`, `backups/` | Рабочие отчёты и резервные копии | Нет |
| `.local/` | Старые сборки, превью, пробы и аварийные дампы | Нет |
| `github-release` | Совместимая ссылка на старые архивы в `.local/` | Нет |

## Права на существующей Kali

Если файлы создавались от root, один раз выполните:

```sh
sudo bash /home/kali/codex-AD/webscanner/scripts/fix_workspace_owner.sh kali
```

Скрипт меняет владельца исходников и `.git`, сохраняя права `scans/`, `backups/` и установленных окружений. После этого выполняйте Git-команды от `kali`, без `sudo`. Из изолированной среды разработки смена владельца недоступна, поэтому этот шаг выполняется на хосте.

## Обычное обновление

1. Меняем код в этой папке и проверяем результат в приложении.
2. Выполняем проверки:

```sh
cd /home/kali/codex-AD/webscanner
bash scripts/check.sh
```

Для первого запуска проверок нужны Python-зависимости из `backend/requirements.txt` и frontend-зависимости (`npm install` внутри `frontend/`). Если используете виртуальное окружение Python, предварительно активируйте его.

3. Смотрим и сохраняем изменения:

```sh
git status --short
git diff --stat
git add .
git diff --cached --stat
git diff --cached --check
git commit -m "Describe the change"
git push origin main
```

`.gitignore` исключает рабочие данные и локальные настройки. Перед коммитом всё равно просматривайте список добавленных файлов. `git add .` запускайте именно из этой папки, а не из родительского каталога.

Если в GitHub появились чужие изменения, сначала сохраните свои коммитом, затем выполните `git pull --rebase origin main`, проверьте результат и отправьте свою ветку. При конфликте разберите его до push; принудительная отправка для обычной работы не нужна.

Изменения на GitHub не перезапускают приложение. Для применения локальных изменений отдельно используйте `docker compose up -d --build`. Перед заменой worker завершите или отмените активные сканы. Не меняйте имя Compose-проекта и учётные данные существующей БД и не используйте `down -v` для обновления.

## Локальный запуск

На этой установке `.env` сохраняет прежнее имя проекта и параметры подключения к БД, а `docker-compose.override.yml` — прежние имена контейнеров. Эти файлы не публикуются. Настройки не меняют уже работающие контейнеры до отдельного запуска Compose.

В новом клоне скопируйте `.env.example` в `.env`, установите собственный пароль и запустите Compose. Без локального override используются стандартные имена контейнеров; UI по умолчанию слушает localhost.

## Старые ZIP

Ранее подготовленные архивы сохранены в `.local/archives/github-release/`. Старый путь `github-release/prepared/` также работает через ссылку. Архивы отражают состояние на момент сборки и больше не обновляются автоматически. Для новых правок используйте этот репозиторий и Git.
